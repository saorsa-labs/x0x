# ADR 0039: Agent Harness Boundary — ACP-Attached Agents vs API-Key Riders

- **Status:** Accepted (2026-08-27)
- **Date:** 2026-08-27
- **Decision owners:** David Irvine (direction), omp (drafting), Claude (review)
- **Reviewers:** David Irvine (approved 2026-08-27)
- **Supersedes:** none
- **Superseded by:** none
- **Related:** ADR-0007 (identity model), ADR-0034 (Leaf default), ADR-0036 (owner singleton), ADR-0037 (placement), ADR-0038 (Home), ADR-0040 (delegation); buzz-pi-acp per-agent key pattern; `src/server/auth.rs`

## Context

Harness processes (pi, omp, and similar agent CLIs) reach x0x from outside
the daemon. Two shapes exist in the field: buzz-pi-acp attaches each agent
as an ACP process that owns a per-agent key file, and API-key minting lets a
harness call an already-running daemon. x0x models neither: `src/` has no
harness concept, one identity per daemon, and the daemon auth token
(`/auth/session`) governs the human REST control plane, not agent
membership (2026-08-23 gap analysis).

## Decision Drivers

- One membership model: identical behavior for Home (ADR-0038) and delegation (ADR-0040).
- The owner's daemon must not become an unscoped signing oracle.
- Harnesses custody keys today; x0x cannot assume daemon-only keys.

## Considered Options

1. ACP-attached only — every harness runs its own daemon/lib instance.
2. API-key riders only — all agents send through the owner's daemon.
3. Both modes over one owner-issued identity (chosen).

## Decision

Define a **sub-agent identity**: the owner key signs an `AgentCertificate`
(ADR-0007) for a fresh keypair generated by the harness and held in a
per-agent key file (buzz `~/.saorsa-keys/` pattern). Two hosting modes:

- **ACP-attached** — the harness process owns the key and connects as its
  own daemon/library instance (the buzz-pi-acp model ported from relays to
  x0x transport). Always `Pinned` to its machine (ADR-0037).
- **API-key rider** — the harness authenticates to the owner's daemon REST
  API with a scoped token; the daemon signs as the registered sub-agent and
  stamps provenance marks on every send. Rider-sourced traffic inherits
  **Leaf** participation (ADR-0034): sub-agents never take pass-through
  gossip duty.

Rider scopes are **deny-by-default** (send to Home + explicitly named
groups, bounded history read), extending the loopback/token auth in
`src/server/auth.rs` with per-agent capability sets — never full daemon
control. Sub-agents appear in `GET /owner/agents` (ADR-0036) and are
Home-eligible via their owner-signed certificate (ADR-0038).

## Consequences

### Positive

- Both paths share one membership model; Home/delegation policy is mode-agnostic.

### Negative / Trade-offs

- Rider mode makes the daemon a signing oracle — scope enforcement is
  security-critical and requires a dedicated deny-by-default test gate.
- Two hosting modes double the auth surface to document and audit.

### Neutral / Operational

- Provenance marks ride envelope metadata; additive, serde-defaulted.

## Validation

- Scope matrix: ungranted verbs return 403; granted sends carry provenance marks.
- ACP-attached instance resolves Leaf, verifies its certificate chain, joins
  Home (ADR-0038 admission); rider token revocation applies on next request,
  no restart.
