Use a portable signed invite and a committed redemption record so any active admin can admit its holder while the issuer is offline.
Separate the invite issuer from the redeeming admin. Retain signature, current authority, owner-certificate, chain and fork checks.
David ruled Q1–Q6 on 2026-10-04 (D99–D105), then round 2 (D117, D118, D120, D130–D133) and round 3 (D145–D148, D157, D159–D165). No question of this ADR's own still blocks Accept; it waits for 0088's acceptance order and the cross-slice receipts (see Rulings and open questions).

## Context

D16 clause 2 requires any active admin to redeem an invite. The [public rulings digest](../design/x0x-direction.md) records that requirement and D54's harness-first rule.
D63 assigns this mechanism to ADR 0112 as Proposed; D58 accepted the contract, not this mechanism.

The offline-inviter gap breaks **L1**: another reachable active admin is insufficient. It also breaks **L2**: waiting for the specific inviter is absent from 0088's eight permitted indefinite blocks.
The gap is named in 0088; #469/#472 track its existing authentication and mandate constraints, rather than a separate S6 bug number.

Current behaviour on `8b35dd1f447774e1a952166f32910fc41b512623`:

| An addressed invite rejects another joiner before consumption. Consumption uses the local issued-invite map. | `src/server/routes/named_groups.rs:13609–13646` |

Changing only the receiver check leaves the local ledger and result pin intact. Copying only that ledger permits another admin to consume the same token independently.
#1139/#818 require verified catch-up when the invite base is stale. #1149/#1150 distinguish a committed seat from current admission and usable keys.
S6 must preserve that distinction and cannot claim to solve re-Welcome on its own.

## Decision Drivers

- An offline issuer or owner device must not prevent an eligible admission.
- The joiner must carry verifiable authorization; no issuer lookup is required.
- A consumed invite must remain consumed after removal, restart and admin handoff.
- Widening redemption requires an explicit **L4** security argument.
- A local lock cannot establish fleet-wide single use during a partition.

## Considered Options

1. **Forward every request to the issuer.** Rejected: it preserves the L1 failure.
2. **Replicate the existing secret ledger without committed consumption.** Rejected: disconnected copies can each spend the token; restart can erase the only receipt.
3. **Drop inviter and mandate checks.** Rejected: it would admit unauthenticated requests and remove the owner's authorization boundary.
4. **Require an online owner, fixed coordinator or admin quorum.** Rejected: each adds an indefinite dependency that D16 and L1 exclude.
5. **Portable authorization plus committed redemption evidence** (chosen as the mechanism). D99 sets its partition semantics. D130 adds one narrow, deterministic replay rule for V5-only sibling branches in OwnerCertified groups (§4a). No other automatic fork winner is chosen.

## Decision

### 1. Capability and portable authorization

Name the registry-v1 capability **`group_invite_any_admin_v1`**.
It means support for the complete invite, redemption, commit, result and persistence contract below. The canonical registry is in the [README](./README.md).
Its number is allocated at acceptance, in acceptance order, as the next free bit in the README registry.
This draft adds no registry row or numeric allocation; the accepting PR adds the row and fixes the number everywhere together.

Use a distinct **InviteV5** canonical view, domain `x0x.invite.v5\0`, and signature domains `x0x.invite.v5.inviter\0` and `x0x.invite.v5.owner\0`. Freeze V4 signed bytes and decoders; do not append inside a positional V4 view.
Keep the link's released parseable shell, `x0x://invite/<base64 JSON>`, with its required parsing fields and `version = 5`; V5 authorization uses only the distinct V5 canonical view. This lets a released V4 parser reach its typed version refusal rather than fail on an unknown URL prefix. The link carries the bearer secret, but the signed view contains only its commitment, as V4's view does.
V5 signs every V4 semantic field plus a random 256-bit `invite_id`, the base policy's canonical `policy_hash`, `max_role = Member` (D103), a mandatory addressed joiner (D99), a mandatory finite `expires_at` (D104) and `redeemer_scope = active_admin`.
The issuer's agent signature and the owner USER countersignature for an owner-axis policy cover the entire view.
The secret commitment is BLAKE3 over the decoded 32 secret bytes; reject ambiguous encodings.
The owner countersignature is the portable permit to execute this invite's single admission.
It authorizes only its addressed agent, and no role above Member or the current policy's permitted role.
The default lifetime is 7 days, the shipped V4 default (`DEFAULT_EXPIRY_SECS`, `src/groups/invite.rs:21`); the maximum is 30 days (D132).
The mint refuses before minting, with a typed terminal refusal: a V5 request with no addressee (`invite_v5_requires_addressee`), with a role above Member (`invite_v5_role_unsupported`), or with no expiry or an expiry above the ruled maximum (`invite_v5_lifetime_invalid`).
Bearer invites and Admin-role invites stay V4 and issuer-pinned (D99, D103). Decoders reject a V5 view with no addressee or no expiry.
Existing creation, expiry, owner pin, policy, base-consistency and size checks remain.
Use S5's single carry/fetch rule for over-budget evidence; add no separate certificate carrier.
**Pre-member roster fetch (D95).** When the base roster exceeds the shipped 20-entry invite cap (#646), the V5 view signs the base `roster_root` and omits the projection. A pending joiner that presents the signed invite binding that root may fetch that one `roster_projection` from any eligible holder under S5's serving guard and limits. It discloses only the root-covered fields the invite already binds. No other pre-member fetch is allowed; S6 adds no further disclosure.

A V4 invite stays issuer-pinned; its signatures cannot authorize V5 scope retroactively. Re-mint it while an authorized issuer is available to gain any-admin redemption.
On an activated group, an S6-aware issuer retains V4 authentication and ledger checks but seals any resulting mutation in the S6 envelope, carrying the existing consumption root. An old binary sees only the legacy placeholder whose non-empty `members_v2` entries are all Removed, preventing creator-to-Admin migration; released-binary reload tests must prove it inert (§5).
V5 support is positive evidence from a current verified, machine-bound ADR 0093 advert, never a version string or AgentCard.
Unknown capability triggers a bounded refresh under D35; it does not authorize a V5 send. While it runs, J's state is the typed wait `awaiting_capability {peer, bit}`; it ends in a send or in `recipient_upgrade_required` (§6).
This positive-advert gate is deliberately stricter than ADR 0093's shipped grant/offer gates, which send on unknown, expired or card-only state. Those 0093 gates remain unchanged; only S6 envelopes require positive support.
Never fall back to a V4 request with V5 bytes or silently change the invite's scope.

### 2. Request, authority and result binding

Send a distinct versioned redemption envelope to a reachable active admin over authenticated, encrypted point-to-point transport; never publish the bearer secret on gossip.
J first tries verified admins from its invite base. For an admin absent from that base, J uses candidate contact hints from existing peer relationships, ordinary group discovery or other reachable holders, then resolves the agent/machine binding with EvidenceV1. These hints confer no authority. Before membership J may fetch only the roster at its invite's root (D95, §1).
For a redeemer in J's invite base, the result carries the intervening events, as ADR 0106 already does.
**Promotion chain (D133).** For a redeemer absent from that base, the result carries that redeemer's promotion chain under ADR 0111's pre-member chain disclosure rule. It carries only the signed chain from J's invite root through that redeemer's promotion to the predecessor, and only on that redeemer's own direct, guarded result path to J. The redeemer sends it only after it has sealed J's add. To verify it, J needs every commit from its invite base to the commit before its own add, so J also sees the other changes made after its invite, such as later joins; David accepted that disclosure (D157), because J is already seated and would see the roster anyway. J verifies the chain before it accepts the result. If it does not verify, J refuses the result with `redeemer_authority_unproven {redeemer}`, and the attempt stays under the failover rule below. No other holder serves the chain to a pre-member, and no gossip carries it. J learns that admin's promotion history before it is a member; David accepted that cost (D133). **L4:** J accepts nothing it cannot verify, and the chain grants no authority beyond this section's checks. **Mixed versions:** only S6 results carry it.
Sending first is safe: the request names that redeemer and the invite names J, so a non-admin recipient cannot use it and no other admin can execute it. The recipient does learn the group, the invite ID and J's identity. No contact with the offline issuer is required.
ADR 0089 EvidenceV1 admission is relationship-scoped and may refuse J's binding lookup to an admin with no relationship; contact hints do not bypass that guard.
The joiner signs the stable group ID, complete invite digest, invite ID, secret proof, joiner ID, **`redeemer_agent_id`**, requested role, key-package digest, certificate digest and attempt nonce.
Here **secret proof** means possession of the canonical bearer secret: the decoded 32 bytes travel only inside this encrypted request, and the receiver checks their BLAKE3 against the V5 signed commitment. The request signature covers those bytes; this is not a zero-knowledge proof. Raw secrets never enter persisted or disseminated redemption proofs.
Bind its KEM key to those same request bytes when that key is used. `request_digest` is BLAKE3 of the canonical signed request preimage under a distinct V5 request domain; it includes the redeemer and nonce. Define a logical `redemption_digest` over the invite digest, joiner, role, key package and certificate; attempt nonces and redeemer IDs are outside that digest so one verified chain can recognize the same admission across retries.
With every V5 request J also signs the secret-free `AdmissionAuthorizationV1` and `AttemptDeclarationV1` (§4a). The redeemer embeds both in the terminal, so a disseminated terminal proves J's consent and its declared attempts without any secret bytes.
Carry the signed invite and required source evidence; fetch missing bytes through S5 from any eligible holder.
EvidenceV1 supplies authenticated agent/machine bindings; it does not prove group-admin authority.

Before mutation, the receiver verifies both invite signatures where required and the joiner's signature and secret proof.
Its agent ID must equal the signed `redeemer_agent_id`; another admin cannot execute a relayed request addressed to this one.
It proves the issuer was authorized at issuance from the verified invite base.
It verifies the issuer's current revocation and authority status as the existing admission path requires. An offline issuer is not a failed authority check.
The receiver independently proves its own active Admin-or-higher seat at the actual predecessor head.
If it was promoted after the invite base, a verified walk must include that promotion.
It checks current policy, bans, revocations, owner certificate, withdrawal/deletion and containment before constructing a candidate.
The redeeming admin and **every enforcing member** require `permit.policy_hash == predecessor policy hash`; a mismatch refuses with typed terminal **`invite_policy_changed`**, with no consumption, seat or key egress. A fresh permit is required. Every enforcing member independently checks the complete signed permit scope against that predecessor: addressed joiner, requested role within `max_role` and policy bounds, issuer authority at issuance and its required revocation/authority status, owner authorization where required, and expiry; the admin's assertion is insufficient.
For live acceptance, each receiver uses its **local wall clock plus the 5-minute skew bound** (D132) to validate expiry and the signed terminal validation time: it accepts a validation time only within 5 minutes of its own clock and before `expires_at`. Catch-up trusts the verified chain's validated time evidence and checks expiry at that committed validation time; it never re-judges historical expiry against "now". The terminal binds that validation time so it cannot be substituted during catch-up.
**Backdating bound (D162).** A terminal's validation time may not be earlier than its predecessor's validation time minus the 5-minute skew; otherwise every enforcing member refuses it with `invite_authorization_invalid {check: validation_time}`. For a replay terminal (§4a) the bound applies to its fresh time only. This limits a partitioned admin's backdating to its own predecessor's time; the remaining harm is no greater than legacy V4 admission.
It never infers current eligibility or confirmed membership from the invite's base-seated snapshot.

Catch up through S3/S5 and normal verified apply before seating; retain the TreeKEM across-gap adoption exclusion.
Bind a result to `(group, invite_id, request_digest, attempt_nonce, redeemer_agent_id, terminal_hash)`.
For a new seat, the authenticated result sender and terminal actor must match the selected redeemer. Verify its authority from the predecessor roster, not from the inviter field or the capability bit.
Changing redeemer starts a fresh nonce and invalidates the previous live attempt under the membership lock.
J signs a new request naming the new redeemer. First query verified committed state through that admin: if the consumption is on its chain, recover the original result without another add.

**Failover rule (D99).** A fresh spend never runs while an earlier attempt may have committed.
- J durably records each attempt `(invite_id, redeemer, attempt_nonce, request_digest)` in its per-group `.s6journal` before it sends it. Every later request in that group carries J's signed list of earlier attempts (§4a widens the lock from one invite to one joiner).
- A redeemer that cannot prove an earlier attempt's outcome on its own verified chain refuses a fresh spend. It returns the typed wait `redemption_unresolved {invite_id, earlier_redeemer, attempt, next_probe_at}`. Absence of a receipt never proves an unspent invite.
- An earlier attempt resolves only in one of two ways. Its commit reaches any holder, and J recovers the original result (below). Or its redeemer returns that commit, or a signed `redemption_not_committed` release. The redeemer signs a release only after it durably records that attempt as refused, so it can never commit it later.
- Every signed pre-mutation refusal from a redeemer is such a release. A release and a commit for one attempt from the same redeemer are signed equivocation evidence under the existing fork rules.
- Local attempt invalidation cannot cancel an already committed remote add.
- **L4:** the rule adds refusals and one signed statement; it relaxes no check. **Mixed versions:** it runs only inside S6 envelopes between nodes with the bit.

**Named amendment to 0088 §2 (D99, confirmed D118).** This ADR amends ADR 0088 §2 with one named entry, ruled by David (D99) and confirmed as a named entry (D118):
**`redemption_unresolved`: an unresolved V5 redemption attempt.** It carries no ordinal, because other slices add their own named entries (for example D76 in ADR 0110 and D96 in ADR 0111). A fresh spend of a V5 invite waits while an earlier attempt at another admin may have committed, and neither that commit nor that admin's signed release is reachable.
- Typed state: the waiting entry `redemption_unresolved`, visible on J's join status. It names the earlier redeemer it waits for.
- Exits: the earlier commit reaches any holder (J recovers the original admission); the earlier redeemer returns its commit or a signed release (a fresh spend may then run at any admin); or the invite's mandatory expiry (D104) ends the attempt with the terminal refusal `invite_expired`.
- Cost: while it waits, this joiner's admission depends on one device, the earlier redeemer. L1 names the original sealer as a device no operation may depend on; David accepted this L1/L2 cost explicitly (D99). The entry covers only this V5 case. It does not cover V4's issuer-pinned waits, which stay tracked defects against L1.

For recovery, the selected admin wraps only the original signed **commit/result** with the fresh attempt binding; verify the original actor independently through S5. The wrapper binds the new request digest/nonce/redeemer to the original request digest and terminal, and checks their identical logical redemption; the original request's redeemer binding is not rewritten. A fetched commit alone does not satisfy the live attempt, and a bare old response cannot confirm it. S5 never serves Welcomes as objects. Lost keys require S8(b)'s separately accepted current-epoch re-Welcome authority; S6 does not turn the original Welcome into an S5 object.

**Attempt windows (D102).** An S6 attempt uses the shipped windows. The TreeKEM **join-result poll** is 120 s (`JOIN_RESULT_POLL_TIMEOUT`, `src/server/routes/named_groups.rs:33213`), with the 115 s Welcome fetch inside it (`WELCOME_FETCH_TIMEOUT`, line 33247). The GSS (non-TreeKEM) join-result poll is 10 minutes (`NON_TREEKEM_JOIN_RESULT_POLL_TIMEOUT`, line 33219). These are two clocks, not one S6 timeout.

**Budgets (D131).** Inside those windows S6 uses these ruled limits:
- **Discovery:** each round tries at most 8 candidate admins, base admins first, with at most 3 EvidenceV1 lookups in flight and one lookup per candidate per 30 s. A round lasts at most 30 s. With no reachable verified admin, J reports `no_reachable_admin` and starts a new round every 5 minutes.
- **Fetch:** S5's ruled values (D98): 10 s inline, 115 s per blob pull, 16 outstanding fetches to 3 holders, one request per digest and holder per 30 s. The D95 roster fetch counts against S5's limit of 8 requests per requester per 10 s.
- **Redeemer:** finish verification and catch-up, or send a signed typed refusal, within 90 s of first receipt for TreeKEM and 9 minutes for GSS, so the answer lands inside J's window.
- **In the window:** the shipped 2 s poll, with a request resend every 3 polls (about 6 s). Each resend is a separately admitted exchange.
- **After an unresolved attempt:** probe the earlier redeemer and up to 3 holders at 30 s, 1, 2 and 4 minutes, then every 5 minutes, with ±10% jitter, until an exit. A probe is a status query, never a fresh spend.

**Pending causes (D117).** A window never ends silently (D64). While a redeemer works on J's attempt, it reports each pending cause with ADR 0108's `JoinPendingNotice` (its §8) (`join_pending_notice_v1`), on J's join-result poll under ADR 0107's guard as ADR 0108 defines it. S6 defines no notice of its own; every S6 node implements that bit. S6 reuses two registered causes: `evidence_pending` (S5) and `authority_catching_up {revision}` while the redeemer catches up within its budget. Citing ADR 0108's cause registry, S6 registers five more, each with its trigger and exit in §6. Each uses only a detail form ADR 0108 §8 allows: no detail, or `count`, `revision` or committed `digests`, and never an agent ID or timestamp. J derives every other field it shows, such as the earlier redeemer and its next probe time, from its own attempt record. Any wider wire detail would belong to ADR 0108 alone.

| Cause | Detail |
|---|---|
| `redemption_unresolved` | none |
| `invite_capacity_exhausted` | none |
| `group_rebuilding` | none |
| `redeemer_state_lost` | none |
| `fork_replay_pending` | `revision` (the fork point's revision) |

ADR 0108 ends an attempt `TimedOut` at its poll deadline. S6 keeps the attempt open past that deadline, as ADR 0108 allows a slice to say: if the window ends with no terminal answer, J moves to `redemption_unresolved`, naming the redeemer it waited for, keeps its verified progress and probes on the D131 schedule. A redeemer never stages a refusal for later pickup. Budget exhaustion never reports keyed-active.

### 3. Owner mandate: explicit L4 amendment

For V5 owner-axis redemption, replace the requirement for a fresh owner-signed terminal mandate with **two signatures**: the owner's portable invite permit and the redeemer's terminal intent.
This is a new acceptance rule, not an absent-mandate grace case.
The terminal intent uses `x0x.owner-mandate.delegated.v1` and a distinct versioned type.
Its canonical preimage retains all **13** shipped v2 bindings, including the actual authority ID and issuance time.
Add the invite digest, invite ID, request digest, attempt nonce, consumption roots before/after redemption and terminal validation time.
Retain the shipped `invite_secret_hash` slot's meaning: BLAKE3 of the canonical secret **string's UTF-8 bytes**, as produced at `src/server/routes/named_groups.rs:22730`. Add the V5 commitment (BLAKE3 of the **decoded 32 bytes**) as a separately named binding in the delegated type; the two hashes are not interchangeable. V4/v2 bytes stay frozen.
Encode fields in the shipped v2 order, then those additions, using fixed-width integers and length-prefixed variable bytes.
The redeemer signs the BLAKE3 digest with its agent key; the permit supplies the independent owner authorization.
Do not substitute the issuer ID for the redeemer or sign a wildcard terminal with the owner key.

Derive the parent, next revision, post-add roster, policy/meta hashes and intended epoch from the actual pre-mutation state.
Every enforcing receiver recomputes the candidate and requires candidate, intent and terminal roster roots to agree before installation.
It also checks both consumption roots, certificate digest, request binding and exact epoch against the terminal.
Every enforcing receiver also applies the full permit-scope acceptance rule in §2, including `permit.policy_hash == predecessor policy hash`, addressed joiner, role cap, issuer authority, required owner signature and expiry; a valid intent signature cannot waive any check.
The certificate must satisfy the predecessor's policy owner and revocation set; certificate and permit expiry follow §2's live-clock/skew and verified-chain catch-up rule.
Signature, sender authority, prev-hash linkage, fork evidence, revocation and epoch entitlement remain fail-closed.
The owner's signed invite lets a different current admin carry out that specific admission. The admin cannot change its recipient, allowed role or policy.
A copied permit alone cannot create an authorized terminal: it still needs the joiner's proof and a current admin signature.
This delegated intent is **not** an owner head attestation or an independent owner fork anchor.
It cannot clear quarantine, select a sibling or evict another member; S3's self-recovery limits remain.
Legacy v2 mandate verification and §1b's per-authority grace states remain unchanged on legacy admissions.
V5 does not enter §1b's absent-mandate grace machine: a missing or invalid permit or delegated intent is the terminal refusal `owner_permit_invalid`. David approved this §1/§1b amendment scope (D105).

An admin demoted on the canonical branch can remain partitioned at a predecessor where it was active. With an outstanding permit and a request signed for it, it can mint an **unanchored sibling seat**. Canonical receivers reject it on their chain; authenticated siblings are fork evidence, not a valid promotion or an automatic winner. Keys delivered on that branch cover only its sibling epoch, never canonical post-demotion epochs. An owner permit is no independent owner head anchor. In an OwnerCertified group, §4a replays that sibling's V5 admissions on the surviving head (D130). If the demoted admin also commits other changes there, demotion precedence settles the fork (§4a, D160).

### 4. Consumption, concurrency and crash safety

Key consumption by `(stable_group_id, invite_id)` and retain `(invite_digest, joiner_id, redemption_digest, original_request_digest, terminal_revision, redeemer_id)`.
Commit a canonical sorted consumption-map root with the membership state in a new versioned S6 commit envelope; disseminated proofs use the signed invite view and secret commitment, excluding raw bearer secrets.
Bind the terminal state hash to the old state-hash inputs plus that root and the S6 protocol version under a new domain.
Every later S6 mutation carries the root forward; legacy mutations cannot erase it.
For an activated group, S4 evictions retain their `MemberRemoved` semantics and payload but are sealed/applied inside the S6 commit envelope and state-hash domain. The consumption root is unchanged by removal. S4's unchanged-encoding claim applies to unactivated legacy groups, not to the enclosing activated S6 commit. A legacy admin may not seal an activated group.
S3/0109 attestation, catch-up, quarantine retirement and re-seat verify the actual versioned S6 hashes and preserve the root; they may not recompute a legacy hash or clear consumption. S7 adoption preserves these sidecars. Neither slice changes the legacy JSON layout.
The acceptance order freezes S4/0110 and S3/0109 before S5 and S6. This ADR therefore **amends 0110 and 0109 only for S6-activated groups** (approved, D105), to bind later `MemberRemoved`/eviction commits and their S3 verification to this envelope/state-hash boundary; leave their Accepted text untouched. Record cross-slice conformance receipts before S6 acceptance, including an S4 eviction followed by S3 catch-up and spent-invite replay as an integration control.
Hash-linked snapshots must include the consumption map; do not reconstruct it from a volatile event log.

Under the membership lock, verify the predecessor and unconsumed ID, build the roster/consumption candidate, seal and persist it with the TreeKEM snapshot before publishing.
Failure installs neither a consumed-only state nor a seat without its consumption proof.
The same logical redemption on the verified chain is idempotent across fresh attempt nonces and creates no second seat, rekey or Welcome. A different joiner or logical redemption, or replay after removal, is refused as consumed; a fresh invite is required.
A new admin must verify consumption state with the head before attempting redemption.
**Mandatory expiry and committed prune (D104).** Every V5 invite expires. Retain its tombstone until the invite has expired and the clock checks pass. Then prune only by a **committed prune mutation from an active Admin-or-higher at the predecessor** that binds the old/new consumption roots, signed invite expiry evidence and terminal validation time. Every enforcing member verifies that authority and each pruned invite's expiry: live receivers use their local clock plus the skew bound; catch-up trusts the verified chain's validated time evidence and never re-judges expiry against "now". Verifiers reject an expired invite even after its tombstone is gone, using the same §2 time rule for admission. Removal or restart alone never prunes it. An admin prunes a tombstone only when its local time is at least `expires_at` plus 10 minutes, twice the skew (D162). **L4:** prune is an admin mutation that every enforcing member re-verifies; it never re-opens a spent invite.
**Storage (D132, D162):** at most 4,096 live tombstones per group, each consumption-map entry at most 256 bytes (about 1 MiB per group), and at most 16 MiB per node. Signed proofs stay in the hash-linked commits under S5 retention (D98), not in the map. Replay may exceed these caps by a bounded overflow (§4a, D163).
**Backpressure** means refusing new mint/redemption work *before mutation*, at either cap, with the typed retryable wait `invite_capacity_exhausted {scope, earliest_prune_at}`, while preserving every existing seat and tombstone and allowing recovery, removals and safe committed pruning. It never means evicting a tombstone to admit another joiner. The wait names `earliest_prune_at`, the first time a prune becomes allowed. Expiry alone never ends the wait.
**Exhaustion exit (D132):** every active admin's maintenance path runs every 5 minutes. On the first pass after `earliest_prune_at`, the designated-first admin (ADR 0110's lowest-eligible-admin rule) commits one prune of every prunable tombstone; any other online active admin commits it on its next pass if nothing has landed. With one active admin online, the wait ends within two passes of `earliest_prune_at`. With no active admin online, it is 0088 §2 item 3.

Two admins with the same predecessor can still sign sibling terminals before they exchange commits. Receipt dissemination and local locking reduce that race but cannot eliminate it across disconnected nodes.
D99 removes the two main sources for one invite. V5 is addressed, so no second joiner can spend it. An honest joiner's failover is refused while unresolved (§2), so no second admin spends it freshly. Idempotence above applies only on one verified chain.
Authenticate conflicting evidence and apply the existing fork rules; never merge consumption maps while ignoring conflicting roster/TreeKEM state.
An ordinary unanchored fork waits for manual admin action under 0088 §2 item 7.
In an `OwnerCertified` group three fork sources remain: a joiner that hides an earlier attempt and asks two admins at once; a fresh invite for the same joiner, redeemed while the first admin's commit is withheld; and the partitioned demoted admin of §3. Without more, each sibling would stay quarantined until an owner-anchored canonical advance under 0064, which is not on 0088 §2, and the portable permit cannot clear it. **§4a resolves each of them without an owner device when the rival branches carry only V5 admissions (D130, D159), or when demotion precedence applies (D160).** Any other fork with two or more non-replayable branches is the named §2 entry `owner_fork_unanchored` (D160). No claim of partition-wide exactly-once redemption is made.

### 4a. Portable admission replay (D130)

D130 makes this S6's OwnerCertified fork-prevention mechanism. David approved it (D159), including its new acceptance rule, retiring a valid sibling, and its exception to ADR 0064 §3 (D146). It applies only to S6-activated `OwnerCertified` groups, Home included. Ordinary groups keep §2 item 7; extending replay to them would amend ADR 0066 and is not proposed.

**Terms.**
- A **V5 admission terminal** is an S6 commit whose only membership change is one V5 redemption: one addressed Member seat and its consumption entry, with the permit, J's admission authorization (below) and the redeemer's delegated intent.
- A **replay terminal** is an S6 commit that re-commits the retired V5 admissions of one fork evidence, and nothing else.
- A **replayable branch** is a sibling branch whose commits after the fork point are only V5 admission terminals, replay terminals and D104 prunes.
- A **demotion-precedence rival** is a non-replayable branch that loses under D160: every commit on it is by the admin that the surviving branch demotes or removes at its first commit.
- The **fork point** is the predecessor that authenticated siblings share (fork evidence under ADRs 0059 and 0064).

**Admission authorization, free of the secret.** With every V5 request J also signs `AdmissionAuthorizationV1`, under its own domain `x0x.invite.v5.admission\0`.
- It covers the stable group ID, invite digest, invite ID, the signed view's secret commitment, joiner ID, requested role, key-package digest, certificate digest and `redemption_digest`. It names no redeemer, nonce or secret bytes.
- The live redeemer first checks the secret proof as §2 requires. It then embeds the authorization in the V5 admission terminal. Its delegated intent binds the same `redemption_digest` and `request_digest`, so it is the redeemer's signed attestation that it checked the secret.
- A terminal never carries J's request or any secret bytes. Every enforcing member verifies J's authorization signature and checks that it matches the terminal's joiner, invite, role, key package, certificate and `redemption_digest`.
- Replay takes J's consent from this authorization, and secret possession from the original redeemer's attestation. It never re-checks the secret. This is part of §4a's new acceptance rule (D159).

**Attempt declaration, free of the secret.** With every V5 request J also signs `AttemptDeclarationV1`, under its own domain `x0x.invite.v5.attempt\0`.
- It covers the stable group ID, invite ID, invite digest, `redemption_digest`, the `request_digest` of the redemption request it accompanies, `redeemer_agent_id`, `attempt_nonce`, and J's declared earlier attempts in that group: the full list of `(invite_id, redeemer_agent_id, attempt_nonce)`, or `attempts_lost_since` after a lost record. It holds no secret bytes.
- The redeemer refuses the request with `invite_authorization_invalid {check: attempt_declaration}` unless the declaration's redeemer, nonce, invite and `redemption_digest` match the request, and its list equals the request's signed earlier-attempt list.
- **Durable carrier.** The redeemer embeds the declaration in the V5 admission terminal, next to the `AdmissionAuthorizationV1`, so it lives on the hash-linked chain under S5 retention. A replay terminal carries it with each retired admission. A node that records `joiner_equivocation` also copies both declarations into its `.s6group`, so the evidence outlives retention.
- **Equivocation evidence.** Two declarations from J for one `(stable_group_id, invite_id)`, naming different redeemers, where neither declares the other's `(redeemer_agent_id, attempt_nonce)`. Any observer verifies both J signatures and both lists, with no secret and no request bytes.

**Joiner lock.** The D99 attempt list covers one joiner per group, not one invite. An admin refuses any new admission of a joiner that declares an unresolved attempt in that group, with `redemption_unresolved`. This closes the fresh-invite source for honest joiners.

**Survivor choice.** Every node that holds the fork evidence computes the same surviving branch:
1. a branch with an owner-anchored advance under ADR 0064 survives;
2. otherwise, if exactly one branch is not replayable, it survives;
3. otherwise, when every branch is replayable, the branch whose first terminal has the lowest terminal hash survives.

Replay terminals count as replayable, so rule 3 also settles two replay terminals that compete at one head.

**Demotion precedence (D160).** If two or more branches are not replayable, and no branch has an owner-anchored advance:
- When one non-replayable branch's first commit demotes or removes an admin, and every commit on every other non-replayable branch is by that admin, the demoting branch survives. If more than one branch meets this, as when two admins demote each other, precedence does not apply.
- The rival branches' V5 admissions replay on the survivor as below. Their other commits, and their prunes, are dropped, because their author has no authority on the survivor. Every replayable branch retires and replays as usual.
- Every enforcing member checks both conditions from the verified chains: the demotion or removal is the demoting branch's first commit after the fork point, and every dropped commit's signer is the demoted admin.

**Named amendment to 0088 §2 (D160).** This ADR amends ADR 0088 §2 with one named entry, ruled by David (D160):
**`owner_fork_unanchored`: an OwnerCertified fork that neither replay nor demotion precedence settles,** for example two admins that demote each other, or two branches with non-V5 commits by different admins.
- Typed state: `fork_awaiting_owner_anchor {fork_point}`, visible on every node that holds the evidence; the group keeps 0064's quarantine.
- Exit: an owner-anchored canonical advance under ADR 0064.
- Cost: the wait depends on the owner's devices. L1 names the owner device as one no operation may depend on; David accepted this cost for this residual (D160).

**Replay transaction.** Every retired branch is replayable, or a demotion-precedence rival. Its prunes are dropped, because the survivor prunes on its own pass. A rival's other non-V5 commits are dropped too, as D160 rules. Its V5 admissions, including those inside any replay terminal it holds, are re-committed, in order, on the surviving head as one replay terminal.
- **Verifying a rival.** Before a rival's admissions count, every enforcing member verifies D160 on that branch alone: the surviving branch's first commit after the fork point demotes or removes admin X; every commit on the rival, from the fork point to its tip, is signed by X; and no other branch also meets D160. The replay terminal lists the hashes of the rival's dropped commits, and every member checks that the list is exactly the rival's commits other than V5 admissions and replay terminals.
- **Expanding a retired replay terminal.** A replay terminal on a retired branch is expanded into the admissions it carries, in its own order. Each keeps its own evidence: the owner permit, J's `AdmissionAuthorizationV1`, and the original admission terminal with its redeemer's delegated intent and validation time. Every enforcing member verifies that evidence as for any retired admission, and also verifies the retired replay terminal's own signer and chain. An entry whose evidence does not verify is refused for that entry, with no seat and no consumption. Expansion goes through nested replays the same way. Each pass flattens one level, so depth is bounded by the number of sibling branches.
- **Deduplication.** Entries are keyed by consumption key `(stable_group_id, invite_id)`, then `redemption_digest`. An entry whose key is already on the surviving head, or earlier in the same expansion, contributes its consumption entry at most once and never a second seat. Two entries with one key but different `redemption_digest` values, for example different key packages, are one invite spent twice. **Total order (D164):** order the retired branches by their first terminal's hash, lowest first; within a branch, keep entry order, with a nested replay's entries at its position, in their own order. The first entry in that order keeps any seat and the invite's one consumption entry; every other entry for that invite adds nothing more. Every enforcing node computes the same order, so all pick the same seat evidence.
- **Under the fork marker.** A node may build, seal or apply a replay terminal while 0064's quarantine for exactly that fork evidence is set. The exception allows one thing: appending one replay terminal on the surviving head, carrying only the retired admissions' seats and consumption entries. It runs no other mutation. Any other quarantine, containment or fork marker on the group still blocks it, and the group then stays `fork_replay_pending`. After the replay terminal is durably installed, and once the head's replays cover the node's whole evidence set (below), the node clears that fork evidence's marker and nothing else.
- **Content.** For each retired admission: the owner permit, J's `AdmissionAuthorizationV1`, the retired terminal as evidence (with the original redeemer's delegated intent and validation time), and a fresh delegated intent from the replaying admin. It carries no J request and no secret bytes. It needs no new request from J. This is the only case in which an admin other than the named redeemer commits J's admission.
- **Two times.** *Historical:* permit expiry, issuer authority and the original redeemer's authority are checked at the retired terminal's validation time, which the verified retired chain already bounds. A permit that expired after that time does not block replay. *Fresh:* the replay terminal has its own validation time from the replaying admin's clock, checked live within the skew like any terminal's. *Current:* the policy hash, bans, removals, revocations, the certificate verdict and whether J is already Active use the surviving head.
- **Outcome per admission.** J not Active: a seat and its consumption entry. J already Active, or the invite already consumed on the survivor: the consumption entry only. A current-state check fails: the consumption entry, no seat, and J's terminal refusal `admission_retired {invite_id, reason}`; J then needs a fresh invite. The consumption key stays `(stable_group_id, invite_id)`, so no invite becomes spendable again.
- **Covered evidence.** Each replay terminal records `covered_evidence`: the sorted terminal hashes of every sibling branch tip it accounts for, under one fork point. With its consumption entries, that defines what it covers.
- **Authenticated coverage.** A replay terminal binds the canonical preimage `blake3("x0x.s6.replay.v1\0" ‖ stable_group_id ‖ fork_point_state_hash ‖ predecessor_state_hash ‖ coverage_count (LE u32) ‖ sorted covered_evidence hashes ‖ replay_content_digest)`. `replay_content_digest` is BLAKE3 over its entries in canonical order. The replaying admin's delegated intent signs this digest, and the terminal's S6 state hash includes it, so the coverage is part of the terminal's identity. Before any coverage counts, every enforcing member verifies, for each covered tip, every commit from the fork point to that tip, so the declared fork point is their common ancestor. It also checks that each covered branch is replayable or a verified demotion-precedence rival, and that the replay's entries are exactly the deduplicated expansion of those branches, minus entries the head already holds. `replay_content_digest` also covers the list of dropped rival commits. A replay missing any proof is refused with `replay_coverage_unproven {fork_point}`. One whose entries do not match its declared coverage is refused with `replay_coverage_mismatch {fork_point}`. Either way it gets no coverage credit and clears no marker, even when its entry delta is empty.
- **Idempotent, and supplemental when evidence grows.** A replay is a no-op when the head's replays already cover every consumption entry the node's authenticated evidence set implies. An admin that has durably installed replays covering its whole evidence set never seals another replay for that set. When a late sibling adds entries that are not yet covered, any admin may seal a **supplemental** replay terminal on the current head. It records the enlarged `covered_evidence` and carries only the uncovered entries. Entries already covered stay idempotent: no second seat and no second consumption entry.
- **Competing replays.** Two admins can still seal replays for one evidence set at one head when the first is withheld. Both are replayable, so rule 3 keeps the lower terminal hash. The other's admissions are already on the survivor, so settling it adds nothing and needs no new commit: a node that holds both clears that pair's marker once the surviving replay is durably installed.
- **Concurrent supplements with different evidence sets (D165).** Two admins can seal supplements at one head H for different late siblings, so the rule-3 survivor at H lacks the other's entries. That makes a **dependent replay fork**: every sibling at H is a replay terminal whose authenticated `covered_evidence` lies under the same original fork point.
  - While the original marker and that dependent marker are both set, any admin may seal one **combining** replay on the rule-3 survivor at H. It covers the union of the siblings' evidence sets, carries only entries not yet on that head, and runs nothing else. Any unrelated quarantine or containment still blocks it.
  - Its coverage is authenticated as above. Once it is durably installed and covers the node's whole evidence set, the node clears the original and dependent markers together, in one durable update that records the combined evidence.
  - **L4:** the exception admits only a replay whose every entry is already authorized by verified evidence under the original fork point. It clears no marker that depends on anything else.
- **Capacity (D163).** Replay never drops a consumption entry. It lands even when it takes the group over the per-group or node cap, by at most the retired branches' entries, so at most (retired branches + 1) × 4,096 entries per group. Until committed prunes bring the group under its caps, new V5 mints and redemptions refuse with `invite_capacity_exhausted`. Seats, tombstones, recovery, removals and prune keep running.
- **Equivocating joiner (D161).** Replay seats each joiner once and never removes one. J's two `AttemptDeclarationV1`s for one invite, naming different redeemers and neither declaring the other attempt, show that J equivocated or lost its record. J keeps the surviving seat. Every node verifies that evidence, keeps it as above, and shows it to admins as `joiner_equivocation {joiner, invite_id}` in the group's diagnostics; an admin may remove J through the normal removal path. Nothing removes J automatically, because an honest joiner that lost its record leaves the same evidence.
- **Who and when (D162).** The designated-first admin at the surviving head (ADR 0110's rule) commits the replay on its 5-minute maintenance pass. Any other online active admin commits it on its next pass if nothing has landed. With no active admin online, the wait is 0088 §2 item 3.
- Until the replay lands, a node that holds the fork evidence reports `fork_replay_pending {fork_point, surviving_branch}` and keeps 0064's quarantine for that group.

**Members of a retired branch.** They drop the retired terminals and their epochs, then follow the surviving branch.
- A member that still holds the fork point's private tree state catches up through S3/S5. J, when its only seat was retired, decrypts the replay terminal's Welcome with its key package's private init key.
- Each member keeps that fork-point state for every V5 admission and replay terminal it applies, and J keeps the init key of each V5 key package, for 30 days, the maximum invite lifetime (D162). After 30 days it deletes them.
- A member without that state, or J without its init key, is a confirmed member with no usable keys. It reports ADR 0114's `confirmed_keys_missing` and takes 0114's manual exit: `manual_reinvite_required`, under the S8(b) manual-exit §2 entry (D118). ADR 0114's automatic repair does not apply, because it needs beyond-retention evidence and a current-tree key proof that a fresh fork does not give. An automatic branch-switch repair would be ADR 0114's to define (open question 1).
- Data written only on a retired branch is not merged.

**Egress.** The replay Welcome and every catch-up artifact go only under ADR 0107's guard and D60, each write admitted under the membership lock (§5).

**L4: retiring a valid sibling.** This is a new acceptance rule, approved by David (D159). It amends ADR 0064 Decision §3, which clears a fork marker only by an owner-anchored advance, for replayable branches and demotion precedence only (D146, D160).
- *Scope:* it retires only branches whose every commit is a V5 admission, a replay terminal or a prune, plus, under demotion precedence, the commits of an admin that the surviving branch demotes or removes at its first commit. A replay terminal is retired only after its contents are expanded and carried forward, so nothing a replay preserved is lost. Otherwise it never retires a role, policy, removal or eviction commit, never chooses among non-V5 siblings and never evicts a member. An owner-anchored branch still wins.
- *Demotion precedence:* the dropped commits were signed by an admin that the surviving branch demotes or removes at its first commit, so on the survivor that author has no authority for them. Its V5 admissions still replay, because their authority is the owner's permit and J's consent, not the demoted admin. Two admins that demote each other settle nothing here; that is `owner_fork_unanchored`.
- *Late siblings:* a sibling that arrives after a replay has landed enlarges the fork evidence set, and rule 3 runs again over every branch. If the late sibling loses, a supplemental replay adds its uncovered entries on top of the existing replay. If it wins, the branch holding the earlier replay retires, and its replay is expanded. Every admission on every branch is still seated at most once, and no consumption entry is dropped. Members switch branch again only with retained fork-point state (30 days, D162), or take the manual exit.
- *Nothing authorized is lost:* each retired admission is re-validated and re-committed on the survivor, or refused with a typed outcome. The owner's permit authorizes the admission, not its predecessor, so re-committing it on another head stays within that authority.
- *Nothing unauthorized is gained:* the replaying admin re-commits only an admission that the owner permitted, J authorized and an admin active at the fork point already committed. A replay cannot change the recipient, role or policy, and every enforcing member re-checks it. Consumption moves with it, so no invite is spent twice.
- *Determinism:* the survivor depends only on authenticated fork evidence. A node that sees one branch keeps it until the evidence arrives, then converges. An admin that grinds a terminal hash to win a tie gains only the epoch choice, because the rival admissions are replayed.
- *Keys:* retired epochs are discarded. Their keys decrypt only data written on the retired branch, by members who were there. No one gets surviving-epoch keys except through normal commits or the replay Welcome, both under ADR 0107's guard and D60. Keeping fork-point state for the retention window costs forward secrecy for that window.
- *Secret:* replay never carries or re-checks the bearer secret. It relies on J's secret-free authorization and on the original redeemer's signed attestation, both made by parties that the retired chain verifies at the fork point.
- *Time:* historical checks use the retired terminal's verified time, and the replay terminal's own time is fresh. So a delayed heal or a permit that expired later neither blocks a valid replay nor admits an admission that was invalid when made.
- *Quarantine:* the marker exception admits only a replay terminal for exactly that evidence, and clears only that evidence after a durable install.

**Mixed versions.** Replay is part of `group_invite_any_admin_v1`. The D101 barrier means every member of an activated group enforces it; released binaries see only placeholders.

### 5. Persistence, compatibility and serving

**Never change the legacy formats.** `named_groups.json` and `home-suite-groups.json` retain their released JSON-map layouts. S6 neither wraps nor replaces either file with binary or JSON-v2. Preserve unaffected entries. Released v0.45/v0.46 readers use `read_to_string` plus `serde_json`; parse errors propagate at `src/server/mod.rs:735–737` and brick startup. ADR 0085 rule 5, D01 and ADR 0094 forbid that outcome.

Put activated state in an S6-owned **per-group sidecar**, `<data_dir>/group-s6/<stable_group_id>.s6group`, encoded as **`X0XNGS6V1\0 || bincode(S6GroupStateV1)`**. It contains the group identity, protocol version, authoritative roster/head, consumption map/root, signed redemption proofs and matching crypto snapshot reference/digest. Outside the committed state, it also holds this issuer's local V4 ledger (`GroupInfo::issued_invites`), which moves here from the legacy entry at activation. The map is never a separately writable ledger. A changed positional layout gets a new magic; keep frozen decoders for every released S6 layout and consume the body exactly.
The corresponding transaction uses **`<stable_group_id>.s6journal`** with magic **`X0XNGS6J1\0`**, and a versioned frozen body. Both magic **and extension** are new: old `*.journal` scans move undecodable entries aside, so a new magic with `.journal` is unsafe. Do not put S6 bytes into `.journal` or `.hsjournal`. Activated crypto snapshots live with the S6 transaction, outside old snapshot names/scans; never serialize transient `PreparedMember` secrets.

**Activation barrier (D101).** A group activates S6 only when every Active member runs S6.
- The activating admin requires, for every Active seat on the predecessor roster, a current verified, machine-bound ADR 0093 advert that sets `group_invite_any_admin_v1`. Under the membership lock it then seals an S6 activation event through the journaled transaction below, and publishes that event only after the transaction is durable.
- Until then the group stays V4. A V5 mint refuses before minting with the typed wait `activation_awaiting_upgrade {members}`, which names each member whose advert is missing, stale or lacks the bit. Exits: each named member publishes a current advert with the bit, or an admin removes that member through the normal removal path. V4 admission keeps working, issuer-pinned. One never-upgraded device keeps the whole group on V4; David accepted that cost (D101).
- After activation, an admin admits a joiner, V4 or V5, only when the joiner's current verified advert sets the bit; the joiner may carry that advert in its request. Otherwise it refuses before mutation with the typed refusal `joiner_upgrade_required`. A released joiner cannot decode that reason and sees its released join-poll outcome; the mixed-version controls record which outcome appears.
- **L4:** only positive, machine-bound adverts count, so no old admin is ever asked to enforce consumption. **Mixed versions:** legacy groups are unaffected; an activated group has no member that cannot read its envelopes.

**Home-policy groups (D81).** Home activation is allowed only behind a released-binary control, as cross-slice rule 1b and ADR 0114 §5 require.
- The Home placeholder uses the same inert roster as any placeholder below. Unlike the non-Home placeholder, it keeps the released-compatible Home identity and policy metadata, and the canonical owner-sync pointer where one exists. A default-policy placeholder with `home = None` fails released v0.46.1 `find_home`/`is_home_candidate`; without an owner-sync pointer, provisioning step 4 can then create a duplicate Home (#449/#824).
- Before any release enables Home activation, the released v0.45.0 and v0.46.1 binaries must load candidate data dirs that hold the Home placeholder **with no owner-sync pointer**, through reload and `provision_home_steps`. They must show no duplicate Home, no `home.json` change, no admin seat, no invite mint and no commit.
- If any variant fails, Home activation stays disabled in that release. A Home activation request then refuses before any sidecar or placeholder write with the typed terminal refusal `home_activation_blocked {failed_control}`. Its exit is a later release whose control passes.
- **L4:** this adds no acceptance rule; it only gates a write. **Mixed versions:** released binaries see an inert Home they cannot act on. Home is an owner group, so its V5 forks use §4a's replay (D130).

At activation of an eligible group, replace its entry in each legacy view where it exists with a placeholder: preserved identity/genesis/revision/hash, default invite-only policy (Home: its preserved Home policy and metadata, above), **non-empty `members_v2` with every entry Removed and no Active seat**, GSS plane, `home = None` for non-Home groups, and no secrets. Released v0.45.0/v0.46.1 run `GroupInfo::migrate_from_v1()` on every entry: an empty `members_v2` would seat the creator as Admin. The non-empty all-Removed roster makes migration a no-op and leaves no admin. Apply it to every alias of the stable ID, including every entry in the Home-Suite view. An old daemon can reserve the ID and load the placeholder, but has no admin seat to mint an invite or seal a membership commit after reload; it does not restore S6 authority. Prove those limits on the released load path. #451's empty-roster placeholder is safe only when a Home-Suite-aware binary replaces it; S6 must not copy that roster shape. Leave existing #451 behaviour unchanged for unactivated groups.
Journal and durably install the S6 backing state and crypto snapshot before replacing the legacy view, retaining the split-store transaction and fsync barriers. Activation remains prepared until every applicable legacy placeholder is durable and the S6 activation commit marker is durable; publish no S6 mutation/key egress before that point. Startup replays the S6 journal before serving the group, rechecking the legacy predecessor/transaction identity; an interrupted activation followed by a legacy rewrite must not clobber the newer legacy head. On S6-aware load a committed sidecar is authoritative. No S6 file fault aborts daemon startup or falls back to legacy state.

**Unreadable S6 files (D120).** S6 quarantines and rebuilds its own files by ADR 0108 §5a's shared lifecycle: classification, the `txid` transaction, resume, history, failure states and fault cases. This section adds only what is specific to S6.
- **Files.** In `<data_dir>/group-s6/`: `<stable_group_id>.s6group`, `<stable_group_id>.s6journal` and the activated crypto snapshot `<stable_group_id>.s6keys`.
- **Reserved prefix and header.** The prefix `X0XNGS6` is reserved for these paths forever; every future S6 format keeps it with a higher version. A header is the prefix, then the kind letter for its path (`V` for `.s6group`, `J` for `.s6journal`, `K` for `.s6keys`), then the version as ASCII decimal digits (1 or more, no leading zero), then one NUL terminator. There is no padding. The highest supported version is 1 for each kind, so today's magics are `X0XNGS6V1\0`, `X0XNGS6J1\0` and `X0XNGS6K1\0`. A journal whose transaction identity does not match the legacy predecessor is also damage.
- **Newer format.** Under §5a's `sidecar_newer_format { file, version }`, the node runs that group memory-only: it writes nothing to that path, and mints, redeems, serves and seals nothing for the group, because each needs durable state (exit: upgrade).
- **This ADR amends ADR 0085 rule 4 for these three S6 files only (D120).** Rule 4 leaves an undecodable file in place for an operator; S6 moves a damaged file aside by §5a and rebuilds what holders can supply. Rule 5 is not amended.
- **Step 4 for each file.** `.s6group`: the rebuild from holders below. `.s6journal`: an empty journal. `.s6keys`: a key-less snapshot marked as lost. Each replacement header records §5a's `rebuilt_from`. For a lost journal or snapshot, step 4 runs in a fixed order. First it durably records, in `.s6group`, the loss marker `journal_lost_since` or `keys_lost_since` together with this `txid` (written as `.s6group.tmp-<txid>`, fsynced, renamed and the directory fsynced, without the lost journal). Only then does it write the replacement journal or snapshot. On resume, step 4 counts as complete only when the replacement lists the `txid` and `.s6group` records the loss for it; otherwise the missing write is done first, the marker before the replacement. The markers only date a loss; they never identify a transaction, which only §5a's `txid` does. If the local clock is behind the rebuilt head's latest validation time, the marker uses that time instead.
- While a quarantine for a group's file is unfinished or its rebuild is running, the group shows `group_rebuilding`; the node never treats it as new or unactivated. Legacy placeholders stay as they are, so a released binary still sees an inert group.
- **Retention (D148).** Quarantined S6 copies follow ADR 0108 §5a's retention rule: they are never deleted automatically, except that a group's copies go when that group's own S6 files are deleted, and diagnostics list each copy with its size.

A V5 invite carries its own authority, so S6 keeps no V5 issuer-only state. The V4 ledger above is the only issuer-local state. David accepted these local-loss outcomes (D147): each loss ends in a typed state with a stated next step, and nothing is silently trusted.
- **Rebuild.** The node gets a verified head through S5's head probe, then the commits and roster through S5, and the consumption map from any S6 holder with `consumption_map {group, consumption_root}`. A holder serves that map only to a requester Active on the committed roster, under ADR 0107's guard, D60 and S5's per-requester limits, in chunks that are each one admitted exchange. The node recomputes the root and the state hash, then installs the rebuilt sidecar through the normal journaled transaction. While it rebuilds, the group shows `group_rebuilding {since, holders_tried}`, and the node mints, redeems, serves and seals nothing for it. With no holder online, this is 0088 §2 item 8. An `absent` answer proves nothing about eligibility: S5 also answers absent when a holder lacks the object or is itself quarantined, withdrawn or unable to serve. So `absent` answers keep `group_rebuilding`. The node reports the terminal `group_state_lost {reason: removed}` only when it verifies a committed removal or ban of its own seat on a verified chain, delivered by the existing removal path; its exit is a fresh invite.
- **Admin journal lost.** The admin cannot tell which attempts it committed or released before the quarantine. For that group it never signs `redemption_not_committed` for an attempt the rebuilt head does not show; a probe gets the pending cause `redeemer_state_lost`, and J stays `redemption_unresolved`. It also refuses to redeem any V5 invite whose signed creation time is before its quarantine time plus the skew, with the signed refusal `redeemer_state_lost {since}`. That refusal promises it will never commit those attempts, but it is not a release, because it cannot say whether it committed one. Other admins can still redeem those invites.
- **Joiner record lost.** J reports `attempt_record_lost {group}`, and its next request declares `attempts_lost_since`. Every redeemer treats that as an unresolved attempt at an unknown admin: `redemption_unresolved {earlier_redeemer: unknown}`. Its exits are the commit reaching any holder, or the invite's expiry with `invite_expired`; no release is possible, because no admin is named.
- **L4:** quarantine weakens no check. Rebuilt state is accepted only when it verifies against a committed head, and the local-only cases refuse instead of guessing. **Mixed versions:** released binaries never read S6 files, and the quarantined copy keeps its bytes for forensics.
Activation is lazy, never a startup migration. Under an ADR 0094 supervised upgrade, defer the **first behaviour-changing sidecar/placeholder write until host commit**, not provisional per-instance health. Before host commit, use rollback-readable state and defer S6 mint/redemption/activation writes, reporting the typed wait `activation_deferred {until: host_commit}`; startup, gossip and polling cannot activate it.

Each slice owns its new state in its own versioned sidecar with a new magic and extension: S4 eviction obligations, S6 redemption state and S8(b) repair state must not rewrite a shared legacy container. S3/S7 operate through the verified group transaction rather than assuming activated authority remains in JSON. Compose sidecars by stable ID and committed head/transaction identity; independently choosing the newest roster and an older consumption root is forbidden. Settle this transaction contract through S6's amendments to already Accepted 0110/0109 and conformance with 0113/0114 before S6 acceptance, without editing Accepted text or assigning S6 ownership of their sidecar layouts.
Real released v0.45.0/v0.46.1 binary tests must show the daemon starts, activated placeholders have **no admin seat after reload, no invite mint and no commit**, ordinary legacy groups still work, and S6 sidecars/journals/snapshots are **verified not to be overwritten or moved aside**. Home-policy groups activate only after the D81 control above passes. Re-upgrade restores the full S6 roster and consumption state; no old placeholder can replace it. Release notes describe group unavailability on downgrade, never daemon unavailability.

**Pre-admission replies (D145).** ADR 0108's `JoinPendingNotice` (its §8) (D117) carries every S6 wait cause to an unseated joiner (§2). S6's signed refusals, releases and probe answers go to that joiner under **ADR 0108's pre-admission signed replies**, its named amendment to ADR 0107 (D145): a signed reply bound to one authenticated, attempt-bound request, carrying no key, Welcome, roster entry or certificate bytes, may go to the requesting joiner's verified machine. ADR 0108 owns that amendment; this ADR reuses it by name and supplies only S6's binding below.
- **S6's binding.** The authenticated request is J's V5 redemption envelope or its status probe. Its attempt is `(group, invite_id, request_digest, attempt_nonce, redeemer_agent_id)`, which J's request signature and `AttemptDeclarationV1` both cover; the redeemer refuses a declaration whose `request_digest` differs from the request's (`invite_authorization_invalid {check: attempt_declaration}`). Its verified ingress is the request's authenticated, encrypted point-to-point session from the machine that J's EvidenceV1 binding names. ADR 0107's full guard and D60 still govern every result, blob chunk, Welcome, key and secret resend.
- **What it covers:** S6's signed terminal refusals (§6), `redemption_not_committed` releases, `redeemer_state_lost` refusals and status-probe answers. The ADR 0108 notice is not a refusal, so it carries none of these. A reply carries no key material, Welcome, group secret, commit or roster. It names objects only by digests that the request or the signed invite already binds; otherwise it names only the kind.
- **Who gets it:** only the requester of a live attempt. The reply answers one authenticated request; it binds `(group, invite_id, request_digest, attempt_nonce, redeemer_agent_id)` and the redeemer signs it. It goes over that request's authenticated, encrypted point-to-point session, to the machine that J's EvidenceV1 binding names. A request replayed from another machine gets no reply.
- **How:** each reply is one admitted exchange, with no hidden transport resend and no gossip or gossip-capable fallback. Immediately before each write, under the membership lock, re-check that the attempt is live and the joiner is not banned or revoked. A banned or revoked joiner gets only its §2 refusal.
- **L4:** these replies disclose nothing beyond what the request and the invite already bind, and grant no admission. **Mixed versions:** they run only inside S6 envelopes; released joiners keep their released refusal receipts, which the same D145 amendment now covers.
0088's own §2 entries remain, with the named amendments other slices add, plus this ADR's `redemption_unresolved` (D99, confirmed D118) and `owner_fork_unanchored` (D160). Issuer-offline is never an entry.

## Consequences

### Positive

- A valid V5 invite can admit through a current admin with no issuer or owner-device round trip on a verified non-conflicting chain.
- Downgrade keeps the daemon and legacy groups running while preserving activated group state for re-upgrade.

### Negative / Trade-offs

- **Home L1 gap:** D81 lets Home activate only after the released-binary control passes. Until a release passes it, an owner device joining Home while its inviting device is offline stays tied to that inviter, the core R3 case. Home is an owner group, so its forks use §4a's replay and demotion precedence, with the residual `owner_fork_unanchored` (D160).
- New wire envelopes and per-group sidecars need an explicit rollout and a shared transaction contract. Tombstones cost storage, bounded by mandatory expiry, committed prune and the D132 caps; long-lived invites must be re-minted.
- **Replay (D130):** a retired branch's data that no other branch holds is not merged. A retired-branch member without fork-point state takes ADR 0114's manual exit. Keeping that state costs forward secrecy for the retention window. Retiring a valid sibling is a new acceptance rule that amends ADR 0064 §3.
- **Unreadable files (D120):** a lost admin journal makes that admin refuse its pre-quarantine invites; a lost joiner record leaves J waiting until the commit spreads or the invite expires.
- **Device-bound wait (D99):** `redemption_unresolved` can depend on the earlier redeemer's device until its commit spreads, it signs a release, or the invite expires. David accepted this L1/L2 cost; it is the named §2 amendment `redemption_unresolved`.
- **Upgrade barrier (D101):** one never-upgraded member keeps its whole group on V4, with the offline-inviter gap.
- **Remaining issuer-pinned paths:** bearer invites (D99) and **Admin-role invites** (D103) stay V4 and inviter-pinned. **Pre-upgrade V4 invites** stay pinned until re-minted as addressed V5. The default V4 mint path keeps this gap. They stay tracked defects against L1, not §2 entries. S6 must not claim all D16 admissions are covered.
- An OwnerCertified fork that neither replay nor demotion precedence settles waits for the owner anchor, the named §2 entry `owner_fork_unanchored` (D160). Ordinary forks need manual admin action (§2 item 7).
- **Promotion chain (D133):** J learns a promoted redeemer's promotion history before it is a member. Lost-key recovery depends on separately accepted S8(b). Unknown capabilities, missing committed receipts and storage pressure produce typed waits/refusals (§6), not keyed-active membership.


### Follow-ups for the implementation

- **Catch-up time (D104):** catch-up trusts the validation time that the redeeming admin bound into the commit, so a partitioned admin could backdate it for receivers that only catch up later. The harm is no greater than what an admin can already do through legacy V4 admission. Open question 4 proposes a backdating bound.
- **Downgrade test:** also assert that the released reload leaves group-scoped data (KV stores, task lists) untouched.
- **Placeholder fields:** list them explicitly. Clear `issued_invites`, `join_requests` and `commit_log`, as #451's `legacy_safe_placeholder` does.

### Neutral / Operational

- V4 signatures, mandates and original-inviter cache repair remain unchanged. V5 is Member-only (D103); David approved the broader amendments (D105).
- Home-policy groups activate only behind the D81 control. S6 preserves owner-certificate checks and revocation eviction semantics. It supplies no new re-Welcome authority or owner fork anchor.
