x0x stores and shares data through authorized peers. It must state who holds the data, how changes merge, and what happens when a peer is offline.

## Context

The product contains key-value stores, task data, local history, file transfer and owner synchronization. Scratchpads are core planned work. Rich collaborative text has a separate parked design.

These data types do not have the same merge, retention or authority rules.

## Decision

We will keep data with explicit holders and scopes. Existing relationships must not depend on a global DHT for user or group data.

Each shared data type must specify its identity, author, permission, merge rule, retention rule and recovery source. Applications must not infer durability from a successful live notification.

Replicated key-value data uses its defined CRDT policy. Last-writer selection can discard a concurrent value. It is not a general collaborative text editor or a transaction service.

Task state follows [A12](A12-r01-agent-teams-delegation-and-task-coordination.md). Membership and key state follow [A08](A08-r01-groups-home-membership-and-repair.md) and [A09](A09-r01-group-encryption-and-key-changes.md). They must not use a data-merge shortcut that changes security authority.

## Synchronization and repair

Use change exchange for prompt updates and a bounded state-repair path for missed updates. The receiver must verify authorship and access before applying data.

A node that returns after an outage must be able to detect missing state. A digest or version comparison may trigger repair. The exact beacon and transfer format require a reviewed specification.

A holder can serve retained data only when the requester is currently entitled to it. The holder must also be entitled to serve it.

A new member does not gain all historical data by default. Each group data type must define the history available at admission and after a key change.

## Owner state and scratchpads

Owner synchronization is limited to its declared state classes. Enrollment, names, profile and group pointers do not imply that all direct-message history or private group data is copied between devices.

Scoped scratchpads will use the group's data and encryption rules. Rider and shared-agent access must be explicit. Scratch access must not expose unrelated stores or daemon state.

Each entry of a group store names its writer (amendment of 16 Nov 2026, #1094 slice P1, revised after review; Claude under David's delegation of 10 Nov 2026 and A15 as amended on 12 Nov 2026). A store record's verified author is not the writer of every entry it carries, because retained images and full state serves relay co-writers' entries. Decision: the writer signs each entry it writes to a store whose topic starts `x0x/group/`, and the mark rides inside the entry in reserved metadata keys (prefix `x0x.writer.`): `x0x.writer.agent.v1` (the writer's agent id, hex), `x0x.writer.sig.v1` (base64 of the ML-DSA-65 signature), `x0x.writer.for.v1` (`<updated_at>:<content hash>`, the version the mark was made for) and, when a rider wrote through the agent, `x0x.writer.rider.v1` (its label, at most 64 bytes). The signature covers the store id, the key the entry sits under, the writer, the content hash, the content type, `updated_at`, the rider label and every other metadata pair, under the domain `x0x.kv.entry-writer.v2`; it leaves out `created_at`, which a merge can change: since 16 Nov 2026 (review of #1974) every merge keeps the earlier `created_at` of the two entries whichever wins, so all replicas at this version converge on it; it stays outside the mark and the LWW order. An owner checkpoint commits to `created_at`. A replica adopts a checkpoint by merging the verified entries into its own under the same LWW rule, so a later local entry or an earlier local `created_at` can win. After 17 Nov 2026 (review of #1987, Claude under David's delegation of 10 Nov 2026 and A15) the replica recomputes the root over its own state after the merge and caches the checkpoint only when it still matches; otherwise it caches none, so it never relays a checkpoint that does not match the entries beside it, and a receiver takes the sender-auth path. The checkpoint's sequence still becomes the replica's high-water mark. The public key is not in the entry: a reader takes it from the keys this daemon has seen proved, by a verified signed gossip message or a verified group mutation (agent id = SHA-256 of the key). A reader gets `verified` (agent and rider), `unverified` (the writer's key is not known here; never shown as verified), `unsigned` (no mark for the current version: an older writer, a rewrite by a writer that does not mark, or a store outside `x0x/group/`) or `invalid` (a mark that does not cover the entry's content, key or store). A delta that holds an entry under another key than its own is refused, so a mark cannot move to another key. No merge path verifies a mark (decision of the reviewer under A15, 16 Nov 2026, reversing an earlier ranked tie-break): verification depends on which keys a daemon knows, and a CRDT merge must be a pure function of the two entries. Every merge path (deltas, SelfKeyed, checkpoints, retained images, legacy history) uses the one LWW rule of `KvEntry::merge`: the greater of `updated_at`, then content hash, then content type, then the sorted metadata. On a tie of time and content the value is identical and only the mark can differ, so the rule keeps one mark the same way on every replica, without checking it. The guarantee is one-way. `verified` with agent A means A signed exactly these bytes for this store and key, so there is no false attribution. The other three states mean "writer unknown" and prove nothing: any group member or relay can replace a mark on such a tie, as any member can overwrite the entry, and a daemon may not know the writer's key. So verification is read-side only (`KvStoreHandle::entry_writer`), and the API and the Scratch app (P2) show `unverified`, `unsigned` and `invalid` as writer unknown, never as evidence of tampering. A rewrite here drops the old mark, and a signing failure leaves the entry unmarked rather than failing an applied put. Entry metadata is already encoded, merged and committed with the entry, so older peers store and relay the mark unchanged: no new wire field, no storage migration and no capability bit, against the versioned-entry plan posted on #1094. A mark adds about 4.7 KB to an entry (at most 4 800 bytes, checked by a test), so a group store of small entries holds about 3 300 of them before its complete image reaches the 16 MiB retained-image limit. A put that would take the image past that limit is refused with `store full` (HTTP 507 on `PUT /stores/:id/:key`), so new and lagging members keep getting the store's history; the image is not paged further. Until 16 Nov 2026 this check ran only on the writer's own node: concurrent writers, or peers on an older version, could still take the merged image past the limit, which #1970 tracks (page the image, or bound incoming merges). Since 16 Nov 2026 the same limit also bounds incoming merges; the next paragraph records that amendment. Slice P2 (16 Nov 2026) shows it: `GET /stores/:id/:key` returns `writer` as `{"verified": true, "agent", "rider"}` only for a mark that verifies for the value returned, and `{"verified": false}` otherwise, without the raw mark keys; a rider's write names the rider's sub-agent id; the Scratch app shows the writer or "Writer unknown", never a warning. Every merge path also refuses an entry whose content hash is not the hash of its value, so two replicas never hold different bytes under one LWW identity.

Group store images have two limits (amendment of 18 Nov 2026, #1970, revised after the review of #2075 and in #2077; this supersedes the #1970 text of 16 Nov 2026; Claude under David's delegation of 10 Nov 2026 and A15 as amended on 12 Nov 2026). This applies to every store that serves its complete state as a retained group image: GroupSigned, Encrypted and TreeKemEncrypted. What is retained is bounded, not only what is live. After every merge (delta, retained image, owner-checkpoint full-snapshot adoption, legacy history import) and every local put or delete, a replica keeps an entry only for a live key. A key removed by any path, an image tombstone included, keeps no value bytes; its OR-Set tombstones stay, because convergence needs them. The OR-Set changelog is cleared, because store deltas are built from the entries and nothing reads it. A snapshot loaded from disk is settled the same way. So the retained size R is the store's whole bincode length, in memory and in the snapshot file. The served image is the same layout with the OR-Set in canonical order, encoded in place, so it is R bytes too. Soft limit, 12 MiB (12 582 912 bytes): a local put that would take R past it is refused with `store full` (HTTP 507). Hard limit, 16 MiB (16 777 216 bytes, the receivers' `MAX_RETAINED_IMAGE_BYTES`, unchanged). This is a store-level admission rule, not part of the entry merge; the entry merge stays the one LWW rule. A merge is applied, settled and measured, and it is kept only when A ≤ 16 MiB. A is the replicated part of R (OR-Set, entries, id, name, policy, owner, writers) plus the larger of 16 KiB and the per-replica fields (version, checkpoint and its sequence, anchor, policy version, ownership conflict, history endorser). Otherwise it is rolled back exactly and fails typed `KvError::StoreFull`. Since R ≤ A, a kept merge leaves R ≤ 16 MiB. Two replicas that reach the same replicated state compute the same A, unless a replica's per-replica fields pass 16 KiB (a checkpoint for a topic of about 10 KB or more). Every input is measured; a back-off never decides admission. Headroom: k writers that start from a common state of S MiB and each write until their own soft gate refuses produce a union of about S + k(12 − S) MiB. Every replica admits every write in any order, and they converge, while that is at most 16 MiB less 16 KiB. More than (16 − S)/(12 − S) such writers can make replicas refuse each other: 2 writers at S = 0, 3 at S = 8, 6 at S = 11. Writers on a version that gates puts at 16 MiB, and writers that bypass the gate, can do the same. So a put can succeed locally and not replicate while the group store is full, and #1970's "refused on every replica" holds only within the headroom. A refusal is visible. `GET /stores` reports `image.state` `full_diverged` with the source (the delta writer or image endorser), the count, the refused size and the next retry time; `x0x doctor` warns. The other states are `ok`, `full` (R above the soft limit: puts refused, merges and serves continue) and `over_limit`. A refusal is logged once per source per retry window (30 s, doubling to at most 30 min). The window only delays this replica's own pulls from that source, through the digest-beacon wake. Three events re-arm every window: a kept merge that shrinks the image, a fast-path delta (a delta whose cached size bound stays under the limit, admitted without an exact measure) whose net entry change is negative, and a local delete. A put that overwrites a key with a smaller value shrinks the image without re-arming; those windows expire by themselves. A merged full image from the source clears its record; a record also lapses one hour after its last refusal. The table is not persisted. Recovery: a refused delta is not kept or re-sent. Its content comes back through anti-entropy: when removals make room, the next digest-beacon repair serves the writer's full retained image, and that merge carries the content. Owner repair: remove entries until the union of the replicas' states fits under 16 MiB less 16 KiB; below 12 MiB puts are accepted again. A delete reaches only keys the deleting replica holds: `DELETE /stores/:id/:key` of a key this replica lacks returns `KeyNotFound`, and no tombstone-by-key path exists. So remove keys your replica holds; a key only another replica holds is removed on that replica (or by its writer). Load from disk: an image saved above 16 MiB by an earlier version loads whole, after its dead entries and changelog are dropped. It reports `over_limit` and logs a warning. Its serves fail typed `StoreFull` and its puts are refused. It admits only merges whose A is at most 16 MiB, so a remote removal that leaves it above is refused, while local deletes always apply. Cost: a delta whose upper growth bound fits a cached bound applies at O(delta). The cache is then refreshed with the exact change in entry bytes, so it stays within a few OR-Set tags of exact. Otherwise, and for every image or adoption, the merge applies in place under an undo journal: displaced entries are moved, not copied, and the OR-Set and small fields are copied. The exact measure walks keys and tags without reading value bytes or allocating. Merges of deltas, retained images and adoption apply in place with no copy of the store; legacy import works on a whole-store copy: the production route clones the destination, runs the kv-layer merge on the clone, and installs the clone on success. Known limits: (a) After a concurrent remove and re-add of a key, replicas can hold the same OR-Set and show different values for that key until anti-entropy runs, and the back-off can delay that run; no honest input leaves a live key with no entry. (b) Every input whose cheap bound is over the limit costs a measure and settle of the whole store (bounded by 16 MiB) under the write lock; this is not rate-limited per source. (c) A stale delta that carries the key in `updated` can bring back a key removed by an image tombstone; no production code builds such deltas, only the public `KvStoreDelta::for_update`. (d) OR-Set tombstones are never collected, so heavy add/remove churn can bring a store to permanent refusal (the cap still holds). (e) Direct `KvStore::put` by library users bypasses the route-level gates. No wire format changes: the served image keeps the `KvStore` bincode layout, older peers decode it, and the `image` field of `GET /stores` is additive. Paging the image past 16 MiB is still not taken.

Retained-image follow-ups (amendment of 20 Nov 2026, #2068; Claude under David's delegation of 10 Nov 2026 and A15 as amended on 12 Nov 2026). This changes two rules of the paragraph above. First, a delta's `updated` entry carries no OR-Set tag, so a replica merges it only into a key it holds live. For any other key (never added, or removed by any path, an image tombstone included) the entry is skipped and no tag is added. This applies to the delta merge of every store policy. Owner-checkpoint adoption is unchanged: it replaces the whole state under an owner-signed content root that must match the delta's `added` and `updated` entries exactly. Known limit (c) no longer holds: a stale `updated` delta cannot bring back a removed key. `KvStoreDelta::for_update` stays public, and its documentation says this. In a SelfKeyed directory such an entry also takes no quota slot, so it cannot push a live key out of the admitted set. New known limit (f): an `updated` entry that arrives before the `added` entry that creates the key is dropped; the value comes back only when an image merge from a replica that holds it heals the store. Second, a removal can make a source's retry due. A kept delta from source S that carries a removal makes this replica's next pull from S due now, even when this replica held none of the removed keys and its image did not shrink. A removal by S can shrink S's image. Two limits stop a writer from defeating the back-off: (i) this re-arm does not reset S's back-off level, because only a merged pull from S clears S's record, and a refused one opens the next, doubled window; (ii) at most one such re-arm per source per window, so removals cost at most one extra pull per window. Known limits (a), (b), (d) and (e) are unchanged. An owner path that removes a key it does not hold is not taken, and neither is a back-off skip when only the values differ; both need a wire change (#2110).

Beacon OR-Set digest (amendment of 21 Nov 2026, #2110 item 2; Claude under David's delegation of 10 Nov 2026 and A15 as amended on 12 Nov 2026; David approved the design on 21 Nov 2026). `StateDigestBeacon` carries an optional `orset_digest`: BLAKE3 over the tag `x0x.kv.orset-digest.v1`, the store id and the bincode of the canonical retained OR-Set (live tags and tombstones in canonical order, the replica-local version and changelog cleared). When a beacon's content digest differs from the local one and the image back-off for its author is active, a beacon whose OR-Set digest equals the local one may skip the back-off, at most once per author per back-off window (the skip resets only when a refusal opens the next window, like the removal re-arm of 20 Nov). Two facts set that bound. First, the OR-Set digest is the sender's claim: a member can copy it from this replica's own beacons, and with a fresh content digest each time the wake gate's pair damping never matches, so without the bound a refused writer would earn a wake per beacon, and a refusal inside the window does not widen it. Second, equal OR-Sets do not mean the author's image fits: values count in the measure, so the merge the skip starts can be refused again. The wake still passes the beacon wake gate, and the merge is measured as before, so a back-off still never decides admission and this rule admits nothing. The local digest is cached at the pair (store version, OR-Set version) and recomputed only when that pair moves: the OR-Set's own version moves on every tag change (put, remove, delta merge, image merge, checkpoint adoption, prune), the store version moves on every merge, a rollback restores the cache with the state, and settling or loading does not change the digest input. An OR-Set merge can leave an empty tombstone slot, so two replicas with the same tags can give different digests; that fails safe to the back-off. Known limit (a) now holds only for a beacon without the field (an older sender) or with a different OR-Set digest. Wire change: one trailing optional field on the last variant field. An older receiver decodes the payload with `bincode::deserialize`, which allows trailing bytes, so it reads `digest` and `entry_count` and ignores the field. An older sender's beacon ends before the field; the decoder then reads EOF and gives `None`, which keeps today's rule. The #1604 fixture for `StateDigestBeacon` changes for this approved wire change, and the main-era bytes are kept as a decode test. Beacons stay sealed-plane only, and storm control guards no KV topic.
Owner removal of a key the replica does not hold (amendment of 21 Nov 2026, #2110 item 3; Claude under David's delegation of 10 Nov 2026 and A15 as amended on 12 Nov 2026; David approved the design on 21 Nov 2026). This corrects the owner-repair text of the 18 Nov paragraph, which said that no tombstone-by-key path exists, and the 20 Nov paragraph, which said that such a path needs a wire change. A removal on the wire already names only the key: the remover sends an empty tag set, and each receiver moves every tag it holds for the key to its tombstones. Every release since v0.9.0 does this. So a removal needs no tag that the remover holds. `DELETE /stores/:id/:key?absent=publish` by an agent that may write the key publishes that removal when the local replica does not hold the key. The local store, its version and its snapshot are unchanged, and the response says `held: false`. Held means this replica holds an entry for the key, the test `KvStore::remove` applies. When the removal of an absent key is neither published nor sent by direct message, nothing happened anywhere and nothing is replayed, so the route answers 503 with `ok: false`. The delta carries no owner checkpoint, because the local state did not change. Without the flag, a key that is not held returns 404 `key not found` (it was a 500). The removal reaches each replica that holds the key and receives the delta live. On a group store (GroupSigned, Encrypted, TreeKemEncrypted) it also spreads from those replicas through retained-image tombstones, so a holder that was offline loses the key at its next image merge with one of them. On a plain store (Signed, Allowlisted, SelfKeyed) cold sync is a full delta, which carries no tombstones, so a holder that missed the delta keeps the key; remove it again when that holder is online. A tag that no receiver held when the removal arrived survives (an OR-Set add wins), and the removal is not replayed (#976). The write rules are unchanged: an AppendOnly store refuses the removal (409), because its receivers never apply one, and an agent that may not write the key gets 403. No wire format change.

Exact delta measure (amendment of 21 Nov 2026, #2110 item 1; Claude under David's delegation of 10 Nov 2026 and A15 as amended on 12 Nov 2026; David approved the design on 21 Nov 2026). This changes the cost rule of the 18 Nov paragraph. A group store keeps its content length (OR-Set and entries) exact, not as a bound. A delta changes it by the exact change in each touched key's OR-Set slots and entry. The slots are counted from `OrSet::retained_tags` (saorsa-gossip-crdt-sync 0.5.95): with an empty changelog, which every settle leaves, the OR-Set encodes to 40 bytes plus, for each live or tombstone slot, the key, a length and 40 bytes per tag. Each key is counted once, also when one delta both adds and removes it; the delta applies its additions, then its removals, then its updates, so such a key ends removed. So while the cached length is warm, a delta into a group store is measured in O(keys in the delta), whether its cheap bound fits or not, and it does not walk the store. Exactly four actions leave no cached length: a local put, a local remove, a local writer mark, and a load from disk. The first delta after one of them measures the whole store once (as before this change) and caches the result. Every merge (delta, retained image, checkpoint adoption, legacy import) leaves the length cached. Changes outside the content carry it across the version bump: an owner announce (a remote input, on both the policy refresh and the recorded owner conflict), an allowlist change and a rename. So no remote input makes a later delta walk the store. A delta whose cheap bound is over the limit first gets a lower bound on its result: a key added and not removed keeps its new tag and the smaller of the local and the incoming entry, any other touched key can lose all its slots and its entry, the name register can shrink to nothing, each allowlist removal frees one agent id, and the per-replica fields count at least 16 KiB. When even that bound is over 16 MiB, the delta is refused, with the same refusal record and log as a measured refusal, before anything is copied or applied. It is a lower bound, so it never refuses a delta that fits. Otherwise the delta applies in place, is measured exactly, and is kept or rolled back as before. Known limit (b) is narrowed, not closed: a delta that passes the lower bound still copies the OR-Set's tags (no values and no encoding) so that a refusal can roll it back, because the 0.5.95 OR-Set gives no per-key tag access for an O(delta) undo; #2146 tracks that accessor. No explicit cap limits the keys in one delta. Every ingress path decodes a delta under a size limit: gossip records, plain and sealed, under 4 MiB (`gossip::wire::decode_delta`), and DM envelopes under 64 KiB. So one delta carries at most about 250 000 removals or about 25 000 entries, and its measure is O(keys in the delta). A fixed key cap could refuse an honest full serve on every retry. Retained images, checkpoint adoption and legacy imports are still measured whole: their input is the whole store. No wire format change.

O(delta) rollback (amendment of 22 Nov 2026, #2146; Claude under David's delegation of 10 Nov 2026 and A15 as amended on 12 Nov 2026). This closes known limit (b) of the paragraph above for deltas. A delta that passes the lower bound and is applied in place no longer copies the OR-Set. Before it applies, x0x starts an OR-Set undo log (`OrSet::begin_undo`, saorsa-gossip-crdt-sync 0.5.96) and saves in it the live and tombstone slots of each key the delta touches (`save_for_undo`, the keys of its `added`, `removed` and `updated`). The other fields of the store (not the entries and not the OR-Set) are still copied, and the entries still roll back from their journal. On a refusal, or on an error while it applies, `OrSet::undo` puts back those slots, the OR-Set version, the changelog floor and the changelog, so the store, its tags and tombstones, and its cached content length are as before the delta. The cost of the rollback state is O(keys in the delta and their tags), not O(tags in the store): the lower-bound step has already compacted the changelog, and `begin_undo` copies only the changelog. The undo log is correct only while no OR-Set element outside the saved keys changes before the undo; the delta apply changes only the keys of `added` and `removed`, and the settle step only compacts the changelog, which the undo log allows. The lower-bound pre-check stays: it refuses a delta before anything is applied or saved. Retained images, checkpoint adoption and legacy imports still copy the OR-Set for their rollback; their input is a whole image, so their merge is of that order too. No wire format change.

Rich-text notes remain parked. If that work resumes, use the accepted Loro direction unless a reviewed revision changes it. Text operations need causal and author checks in addition to group encryption.

## File transfer and retention

A file transfer must bind the declared content identity, size and recipient. Check the complete content hash before reporting verified completion.

File control frames have an application acknowledgement (accepted by David, 12 Oct 2026, option (b); archived as [T-file-control-ack](../../adr-archive/transient/T-file-control-ack.md)). `FileMessage::ControlAck` (wire tag `file-control-ack`) names the transfer id and the operation: `offer`, `accept` or `reject`. Capability bit 3 is `file_control_ack_v1`; this allocation does not edit archived ADR 0093. A node waits for the acknowledgement only when the peer's current verified advert sets bit 3, and a missing acknowledgement then fails the call. A verified advert without bit 3 is a v0.47.0 peer: do not wait, do not send the frame, and a stored offer is success. With no verified advert, do not wait but still send the frame. A chunk acknowledgement whose id is `ctrl:<op>:<id>` must not complete the wait, an acknowledgement from any other agent must not complete it, and history classifies the frame as ephemeral.

Bound transfer size, concurrency, temporary storage and retained content. An interrupted transfer must have a clear retry or cleanup result.

Deletion has a defined local or replicated meaning. It does not promise erasure from another participant's backups or previously exported plaintext.

A local acknowledgment must state what was saved. It must not imply that a remote replica or backup exists.

## Consequences

Each data type has an explicit merge and retention contract. Peers can work during a partition, but availability still depends on authorized holders. Applications must expose conflicts, replica state and storage limits.

## Alternatives

A global storage layer could offer broader availability, but would change custody, cost and trust assumptions.

Using one whole-document last-writer value for every data type is simple, but can discard edits that users expect to merge.

## Current implementation

KV stores, task lists, file transfer and scoped owner sync exist. The full scratch-store surface and several any-holder recovery paths remain work in progress. Rich-text work remains parked.

## Validation

Test concurrent edits, missed updates, restart, owner-offline repair, corrupted files and storage limits. Verify deterministic merge behavior and author checks.

Test removal during fetch and key delivery. Confirm that an unauthorized rider cannot recover another scope through a history or repair endpoint.

## Matters to settle

Set retention and storage budgets per data class. Define which authorized peers must hold a copy before the product reports replicated durability.
